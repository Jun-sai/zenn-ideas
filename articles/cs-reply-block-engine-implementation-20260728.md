[前回の記事](https://zenn.dev/jun_sai/articles/cs-reply-as-execution-gate-20260728)で、CS対応の返信文生成を「実行ゲートを決めるための、判断の連なり」として再定義した。ここでは、その骨格を実際にどう組むか、という話をする。

## 1. ブロックという単位

判断の最小単位を、本記事では**ブロック**と呼ぶ。ブロックとは、ある状態(state)の条件を満たすと独立に発火し、返信文に載せるべきアクションを一つ追加する、という単位のことだ。複数のブロックがそれぞれの条件で同時に(OR結合で)発火し、発火したブロックの組み合わせが最終的な返信文になる。「診断が確定したら交換を提案する」「責任の所在が不明なら共感の一言を添える」といった個々のルールが、それぞれ1つのブロックにあたる。

役割で分けると、ブロックは**温度感対応・情報収集・回答案内・対応実行・保留接続・クローズ**の6グループに分かれる。感情面のケア、事実確認、情報提供、実際のアクション、結論を保留してつなぐ処理、締めの挨拶、という6つの機能に対応している。

「不具合か、使用者側の問題か」を見極める判断は、多くの現場で**未構造化**なまま運用されている。未構造化というのは、判断基準がどこにも書き出されておらず、経験を積んだ人の頭の中にだけチェックリストとして存在している状態のことだ。書かれていないので、引き継げない、抜け漏れがあっても気づけない、部分的にだけ自動化することもできない。

これは商品×症状×パーツのマトリクス(確認すべき事項+不具合と判定する要素)として書き出すことで、構造化・自動化しうる対象になる。頭の中にしかなかった暗黙知を、検索可能な表に変換するということだ。

### ブロックの正体 ー ルーチンの熟達と適応的熟達

この「ブロック」という単位そのものが何なのか、認知科学の枠組みを借りて整理しておく。ブロック(診断マトリクスや温度感対応などの型)は、**「ルーチンの熟達」の外部化**だ。これまで蓄積されてきた「こういう時はこう判断する」という経験の結晶を、誰でも参照できる形に取り出したものにすぎない。

一方で、ブロックそのものを組み替える力ー新しい状況に出会ったときに、既存のブロックのどれが当てはまらないかを見抜き、粒度を調整したり新しいブロックを追加したりする力ーは、これとは別の**能力**だ。認知科学ではこれを「適応的熟達(adaptive expertise)」と呼び、決まった手順を速く正確にこなす「ルーチンの熟達(routine expertise)」とは区別する(Hatano & Inagaki, 1986)。

この区別が重要なのは、システムが自動化するのは前者(ルーチンの熟達の中身)だけで、後者(ブロックを設計・改訂する力)は自動化の対象にならない、という線引きができるからだ。ブロックが増えても、ブロックを組み替える人間の役割は消えない。

### なぜこの3つを区別するのか ー 原理・能力・未構造化

判断を人間に残すかどうかには、実は理由が3種類あり、それぞれ時間による動き方が違う。

| 分類 | 意味 | 動き方 |
|---|---|---|
| 原理 | 不可逆・対外責任・金銭・価値判断だから、人間に残す | AIがどれだけ進歩しても動かない |
| 能力 | 今のAIには荷が重いだけ | 実績と技術の進歩で動く |
| 未構造化 | 判断基準がまだ頭の中にあり、明文化されていないから渡せない | 明文化の作業そのもので動く(いわば「仕事の在庫」) |

ここまで扱ってきた「未構造化」な診断や、「能力」としてのルーチンの熟達/適応的熟達は、この分類でいう②③にあたる。一方、実行ゲート(金銭・不可逆な対応の承認)は①の「原理」にあたる。これだけは、診断の自動化がどれだけ進んでも、人間に残り続ける判断だ。

理由を書かずに分類すると危険もある。本当は書き出せば済む「未構造化」を、「これはAIの能力の限界だから仕方ない」という言い訳に使ってしまう、というようなことが起きる。分類には、理由と「何が変わったら見直すか」を必ずセットで書く必要がある。

## 2. アーキテクチャ全体

```
① state抽出       顧客メッセージ → 後続対応か・診断フラグ(事実面のみ)
                  ※注文番号欠落時や症状の特定は、プルダウン選択で人間が確定させる(AI依存を減らす)
② ブロック発火     state → 条件を満たしたブロックが独立にアクションを追加(OR結合)
③ テンプレート結合  発火したアクション → 固定順序で文章を結合
④ 温度感の味付け   人間が温度感(低/中/高)を判断し、文章全体に反映。トークン量も温度に応じて調整
⑤ 顧客同意ゲート   会社がコスト(情報開示・物流)を払う前に、顧客の条件同意を得る
⑥ 実行ゲート       金銭・不可逆な対応の承認は、常に人間が行う(原理)
```

交換・返金など金銭が動き後戻りできない実行の承認は、診断の精度によらず常に人間が行う。「原理」はここにのみ適用され、診断の自動化がどれだけ進んでも動かさない一線として設計している。

ブロックを独立発火・OR結合にすることで、main処理は「ループ→条件判定→アクション追加→結合」という汎用ルールエンジンになり、複雑さはすべてブロック(データ)側に移動する。

## 3. 温度感 ー 最後に乗せる「味付け」

当初、温度感は最初に判定して他ブロックの発火に影響させる案だった。だがこれは、事実の判断(何が起きたか・何をするか)と感情の伝え方(どう届けるか)を同じレイヤーで混在させてしまう。そこで温度感は、**他ブロックが確定した後に、人間が最後に乗せる味付けレイヤー**として切り離した。

味付けは冒頭・末尾の一言だけでなく、文章全体に及ぶ。温度感が高い顧客ほど言葉選びに丁寧さが必要なため、そこにかけるトークン量が増えることを許容する。

```
低温:  ブロック結合のみ、AI不使用(最安・完全決定論)
中温:  つなぎ目だけAIが整える(軽い一手間)
高温:  文章全体をAIが温度に合わせて書き直す(トークンをかけてよい)
```

重要なのは、温度がどれだけ上がっても、書き直されるのは**言い回しだけ**で、ブロックの発火(何を伝えるか・どのアクションを取るか)は温度と無関係に決定論的なまま保たれることだ。圧縮・再現性・監査可能性が必要なのは「何を決めたか」の部分であり、そこは温度に左右されない。トークンを使ってよいのは「どう伝えるか」の部分だけで、価値が出るところにだけ予算を割く設計になる。

この分離は、人間の関与ポイントを2種類に整理する意味も持つ。実行ゲート(原理・ガバナンス、常に人間)とは別に、温度感の味付け(感覚的な判断、人間の勘を意図的に残す領域)という、性質の異なる2つ目の人間タッチポイントができる。

## 4. ロールプレイで検証してわかったこと

この型が本当に機能するか、2つの対照的なケース(不具合・実行系のケースと、顧客都合・返品返金のケース)をロールプレイで通して検証した。

見えてきた共通の骨格は次の4つだった。

1. 診断・ポリシー該当性が確定するまで、実行系アクションは発火させない(原理は実行承認のみに適用する)
2. 確定には自己申告ではなく証拠を求め、証拠が不十分なら再依頼で粒度を上げる
3. 企業側がコストを払う前に、顧客側の意思・条件同意を確認するゲートを挟むと、無駄な手戻りを防げる
4. 温度感対応のブロックは「責任が確定しているか」で謝罪と遺憾を切り替える必要がある

同時に、検証を通じて見つかった追加の設計要素もある。実行系アクションには、実行前に確定すべき付随情報とペアで発火するブロックが必要な場合があること。原状確認などの前提条件は、自己申告ではなく証拠を求める運用にすること。顧客都合の費用に関する質問は、社内規定が明文化されていればテンプレート化できるが、されていなければ原理側(エスカレーション)に倒れること。

## 5. ブロックはどれだけ使い回せるか

2パターンのロールプレイで発火したブロックを、種類として集計してみると、3つの層に分かれた。

- **完全共通(ロジック同一、パラメータだけ違う)**: 注文情報照合、視覚的証拠依頼、実行ゲート画面、温度感ルーティングなど
- **骨格共通+アルファ(個別ロジックが要る)**: 実行+付随ステップのペア発火、規定説明、顧客同意ゲートなど
- **完全に個別**: 商品×症状×パーツ診断、症状ごとの事実確認・トラブルシュート質問

たった2パターンの比較だけで、種類ベースの7〜8割が前の2層(完全共通・骨格共通+アルファ)に収まり、新規ロジックが必要だったのは最後の層だけだった。パターンを増やすほど、この比率はさらに共通側に寄っていくと見込んでいる。この最後の層さえチェックリスト化できれば、あとは汎用エンジン+データ(ブロック定義)だけで全体を実装できる、という見通しの根拠になっている。

## 6. 実装で見えた設計上の帰結

この骨格は、軽量な仕組み(スプレッドシート程度)でも実装できる設計にしてある。ポイントは、知識の性質によって扱い方を分けたことだ。増え続ける診断知識(商品×症状の組み合わせ)は検索型で持たせ、増えにくい共通ルール(ブロック定義)は一覧型で持たせる。性質が違う知識を同じ構造で扱おうとしないことが、軽さの理由になっている。

この分け方をすると、main側の処理は「照合→ループ→並べる→ゲートに回すかの判定」という汎用ルールエンジンだけになる。個社差分・商品差分はコードの外、データ側に閉じ込められる。state抽出のボトルネックも、AIに読ませる部分をなるべく減らし、人間が選択肢から確定させる形に寄せることで、必要ならAI呼び出しゼロでも動く設計にできる。

## 7. 業種を跨いで検証してわかった、最終結論

この型を、性質の異なる複数の業種に机上で当てはめてみた。実データでの検証ではなく、あくまで型を当てはめてみた段階の検証であることは断っておく。

概ね、そのまま流用が効いた。6グループの分類、実行ゲート、顧客同意ゲート、診断マトリクス形式は、業種が変わっても名前を変えるだけで機能した。変わるのはブロックの中身(条件と文言)だけだ。

ただし1点だけ、業種ごとの調整が必要になる。**「原理」を発動させる条件のリスト**だ。今回の基準は「金銭・不可逆」だったが、業種によっては金銭が動かなくても、本人確認を誤ることが不可逆な事故につながるケースがあり、その場合は「本人性・セキュリティ」のような条件が原理側に加わる。承認の階層(誰が、何段階で承認するか)も、扱う金額規模や業種によって変わりうる。

**型(6グループ・ゲート構造・マトリクス形式・main)は業種を問わず共通。業種・会社ごとにカスタム設計が必要なのは、「原理(人間承認必須とする判断)の線引き」のみ。**

汎用の部分と、原理の線引きの部分とでは、性質がかなり違う。こういう商売の形もあり得るかもしれない、とまだ考え始めている段階だ。

判断の連なりを支える、という前回の話に戻れば、この型が最終的にやっているのは、「何を人間が決めるべきか」を先に決め切ることだ。それ以外は、全部データにしてしまえる。
